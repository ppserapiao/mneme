# mneme Protocol — v0.1 (Draft)

**Status**: Draft. Subject to change before v1.0.0.
**Date**: 2026-05-19.
**Editor**: mneme contributors.

This document specifies version `0.1.0-draft` of the **mneme Protocol** — the open, vendor-neutral interface for user-sovereign AI memory. The protocol describes the shape of a memory record, the verb set every conforming implementation must expose, the wire format for those verbs, and the closed set of errors a store may surface.

The protocol is the boundary mneme publishes. Anyone may implement it. The TypeScript reference implementation lives at [`@mneme/sdk`](../../packages/sdk); the canonical TypeScript types live at [`@mneme/protocol`](../../packages/protocol); the architecture and threat model live in [`ARCHITECTURE.md`](../../ARCHITECTURE.md).

## 1. Conventions

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

JSON examples follow [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259). Timestamps are [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) (ISO-8601 subset) with timezone offset and millisecond precision.

## 2. Terminology

- **Memory record** — the atomic unit of memory. A signed, immutable JSON object as defined in §3.
- **Owner** — the human or agent on whose behalf records are written. Identified by an opaque `ownerId` string.
- **Store** — any system that implements the verb set in §4 over a collection of memory records for one or more owners.
- **Client** — any code (SDK, MCP server, app) that talks to a Store on behalf of an Owner.

## 3. Data model

### 3.1 MemoryRecord

A memory record MUST be a JSON object with the following shape. Field names are case-sensitive.

```json
{
  "id": "01ARZ3NDEKTSV4RRFFQ69G5FAV",
  "ownerId": "pedro@example.com",
  "kind": "preference",
  "body": { "mode": "plaintext", "data": "Prefers concise code review comments" },
  "embedding": [0.012, -0.418, /* ... */],
  "metadata": {
    "createdAt": "2026-05-19T12:00:00.000Z",
    "sourceApp": "claude-code",
    "sourceContext": "in PR #42 review thread",
    "confidence": 0.91,
    "tags": ["code-style", "review"]
  },
  "lifecycle": {
    "supersededBy": null,
    "expiresAt": null,
    "forgetAt": null
  },
  "signature": null
}
```

| Field        | Type                | Required | Notes |
| ------------ | ------------------- | -------- | ----- |
| `id`         | ULID string         | yes      | 26 characters, Crockford base32. Client-generated. |
| `ownerId`    | string (1–256)      | yes      | Opaque to the Store; treated as bytes. |
| `kind`       | `MemoryKind`        | yes      | See §3.2. |
| `body`       | `Payload`           | yes      | Discriminated union, see §3.3. |
| `embedding`  | `number[]`          | no       | Finite float values; dimension is implementation-defined. |
| `metadata`   | `MemoryMetadata`    | yes      | See §3.4. |
| `lifecycle`  | `MemoryLifecycle`   | yes      | See §3.5. May be `{}`. |
| `signature`  | string              | no       | Ed25519 signature, base64url. OPTIONAL in v0.1, REQUIRED from v0.2. |

Records are conceptually immutable. "Edits" produce new records that supersede older ones via `lifecycle.supersededBy`. Stores MUST NOT mutate `id`, `ownerId`, `kind`, `body`, or `metadata.createdAt` after initial write.

### 3.2 MemoryKind

`kind` MUST be one of the following string literals:

| Value          | Intent |
| -------------- | ------ |
| `fact`         | An assertion about the world (e.g., "Pedro is based in the UK"). |
| `preference`   | A stable user preference (e.g., "prefer TypeScript over Python"). |
| `event`        | Something that happened at a point in time (e.g., "shipped v0.1 on 2026-06-15"). |
| `relationship` | A connection between entities (e.g., "works with collaborator X"). |
| `context`      | Longer-form situational context that does not fit the above. |
| `skill`        | Procedural memory for agent use (a learned how-to). |

Stores MUST reject unknown kind values with `invalid_record`. Future versions of this protocol MAY extend the enumeration; clients MUST treat any unknown future kind as `context` for backwards compatibility.

### 3.3 Payload

`body` is a discriminated union over `mode`. v0.1 defines two modes.

**Plaintext** — permitted for development and local-first SDK contexts. Stores accepting writes from untrusted clients SHOULD reject this mode.

```json
{ "mode": "plaintext", "data": "Prefers concise code review comments" }
```

**AES-256-GCM (envelope encrypted)** — the production mode. The `wrappedKey` is the per-record data key wrapped under the Owner's master key (key management is out of scope for v0.1; see [ARCHITECTURE §5](../../ARCHITECTURE.md#5-encryption-model)).

```json
{
  "mode": "aes-gcm-256",
  "ciphertext": "<base64url>",
  "nonce": "<base64url>",
  "wrappedKey": "<base64url>",
  "aad": "<base64url, optional>"
}
```

When `aad` is present, it MUST include the record `id` to prevent ciphertext substitution between records. Future modes (e.g., `aes-gcm-256-pir`, `chacha20-poly1305`) MAY be added in subsequent versions.

### 3.4 MemoryMetadata

| Field           | Type        | Required | Notes |
| --------------- | ----------- | -------- | ----- |
| `createdAt`     | RFC 3339    | yes      | Client wall-clock time. |
| `sourceApp`     | string      | yes      | Free-form identifier of the originating app (e.g., `claude-code`, `chatgpt-web`). |
| `sourceContext` | string      | no       | Free-form context string. MAY be encrypted in production. |
| `confidence`    | number      | no       | Model-assigned confidence in `[0, 1]`. |
| `tags`          | string[]    | no       | Up to 64 tags, each 1–64 chars. MAY be encrypted in production. |

### 3.5 MemoryLifecycle

| Field           | Type       | Notes |
| --------------- | ---------- | ----- |
| `supersededBy`  | ULID       | If set, points to the newer record that replaces this one. |
| `expiresAt`     | RFC 3339   | Soft expiry. Stores MUST omit expired records from `SEARCH` and `READ` results. |
| `forgetAt`      | RFC 3339   | Hard-delete schedule. Stores MUST permanently remove the record once this timestamp is reached. |

All three fields are independently optional. Stores MUST treat `expiresAt <= now` and `forgetAt <= now` as terminal: such records MUST NOT be returned by `READ` or `SEARCH`.

## 4. Verbs

A v0.1-conforming Store MUST implement the following verbs. Verb names in this section are normative; their concrete bindings (HTTP method + path, MCP tool name, function signature) are defined per-transport in §5.

### 4.1 WRITE

Persist a new memory record. Returns the canonical stored form (with any server-assigned fields populated).

**Input**: `{ ownerId, kind, body, metadata? }` — `metadata.createdAt` MAY be omitted; the Store MUST populate it.

**Output**: full `MemoryRecord`.

### 4.2 READ

Fetch a single record by ID.

**Input**: `{ ownerId, id }`.

**Output**: `MemoryRecord` or `null` if no record exists for `(ownerId, id)`. Cross-owner access MUST return `null` rather than the record from another owner.

### 4.3 SEARCH

Return ranked records matching a natural-language query.

**Input**: `{ ownerId, query, limit?, kinds? }`. `limit` defaults to an implementation-defined value (RECOMMENDED: 10) and SHOULD be capped (RECOMMENDED: ≤100).

**Output**: array of `{ record, score }` ordered by descending score. The score is implementation-defined; higher MUST mean more relevant.

Stores MUST exclude records where `lifecycle.supersededBy` is set, `lifecycle.expiresAt <= now`, or `lifecycle.forgetAt <= now`.

### 4.4 FORGET

Mark a record as forgotten. Soft by default (sets `lifecycle.expiresAt = now`); when `hard: true`, additionally sets `lifecycle.forgetAt = now` to schedule permanent removal.

**Input**: `{ ownerId, id, hard? }`.

**Output**: none. MUST return `record_not_found` if `(ownerId, id)` does not exist.

### 4.5 SUPERSEDE

Atomically replace an existing record with a new one. The old record's `lifecycle.supersededBy` is set to the new record's `id`; the new record is otherwise a normal `WRITE`.

**Input**: `{ ownerId, supersededId, replacement }` where `replacement` matches the `WRITE` input shape.

**Output**: the new `MemoryRecord`. MUST return `record_not_found` if the superseded record does not exist.

### 4.6 EXPORT

Stream every record (including superseded and forgotten) for an owner.

**Input**: `{ ownerId, since? }`. When `since` is present, only records with `metadata.createdAt >= since` are returned.

**Output**: ordered stream of `MemoryRecord`, ascending by `createdAt`.

### 4.7 OBSERVE (deferred to v0.2)

A subscription verb for change notifications is intentionally omitted from v0.1. It lands in v0.2 alongside the sync engine and uses Server-Sent Events on HTTP transports.

## 5. Transports

v0.1 specifies a single normative transport. Additional transport bindings (MCP, gRPC, binary) are tracked in [ARCHITECTURE §7](../../ARCHITECTURE.md#7-api-surface).

### 5.1 HTTPS + JSON

| Verb       | Method | Path                                  |
| ---------- | ------ | ------------------------------------- |
| WRITE      | POST   | `/v1/memories`                        |
| READ       | GET    | `/v1/memories/{id}`                   |
| SEARCH     | POST   | `/v1/search`                          |
| FORGET     | DELETE | `/v1/memories/{id}`                   |
| SUPERSEDE  | POST   | `/v1/memories/{id}/supersede`         |
| EXPORT     | POST   | `/v1/export`                          |

All requests and responses MUST be `application/json; charset=utf-8`. Authentication MUST be either:

- a signed JWT in the `Authorization: Bearer <token>` header, where the signature is Ed25519 over the request body, OR
- an opaque bearer API key issued out-of-band (HTTPS only).

The signed-JWT mode is REQUIRED for production stores from v0.2 onward; v0.1 permits opaque keys to ease bootstrap.

All responses MUST include a `Mneme-Protocol-Version` header containing the protocol version the Store implements (e.g., `0.1.0-draft`).

## 6. Errors

A Store MUST surface failures as one of the following error codes. Transports map these to native error shapes (HTTP status codes, MCP error responses, exceptions).

| Code                            | HTTP | Meaning |
| ------------------------------- | ---- | ------- |
| `invalid_record`                | 400  | The record or input does not conform to this spec. |
| `record_not_found`              | 404  | The requested `(ownerId, id)` pair does not exist. |
| `unauthorized`                  | 401  | The caller is not authenticated or lacks access. |
| `rate_limited`                  | 429  | Per-key or per-owner rate limit exceeded. |
| `storage_failure`               | 500  | An internal Store failure. The error message SHOULD NOT leak sensitive detail. |
| `unsupported_payload_mode`      | 400  | The Store does not accept the supplied `body.mode` (e.g., plaintext in production). |
| `protocol_version_mismatch`     | 400  | The client and Store cannot negotiate a compatible protocol version. |
| `conflict`                      | 409  | A SUPERSEDE or WRITE conflicted with concurrent state. |

Error response body:

```json
{ "error": { "code": "record_not_found", "message": "no memory 01H... for owner" } }
```

## 7. Version handshake

Clients and Stores both advertise their supported protocol version(s). The `Mneme-Protocol-Version` request header on writes MUST match a version the Store accepts; otherwise the Store MUST reply with `protocol_version_mismatch`. Stores SHOULD support the current minor version and the immediately previous minor version for at least 18 months.

## 8. What is **not** in v0.1 (and why)

The following are explicitly deferred. Each will land in a future minor version with a dedicated section here.

- **Key management ceremony** (passphrase derivation, device pairing, recovery phrase). The encryption envelope shape is specified; the ceremony around it is not.
- **Sync protocol** (CRDT messages, conflict resolution semantics). Lands in v0.2.
- **MCP tool mapping** (`mneme_write`, `mneme_search`, etc.). Lands in v0.2; semantics will mirror the verbs in §4 1:1.
- **OBSERVE** verb (subscribe to changes). Lands in v0.2.
- **Encrypted vector search** (PIR, LSH-on-client). Lands in v0.3.
- **Share** verb (granting another owner read access to a record). Lands in v0.4.

Anything not in this document, the canonical schema (`@mneme/protocol`), or the conformance suite (`tests/conformance/`) is implementation-defined.

## 9. Conformance

The reference conformance suite lives at [`tests/conformance/`](../../tests/conformance). An implementation is "v0.1-conforming" if and only if it passes every test in that suite against its public verb set, with no skips. Implementations MAY pass additional tests; they MUST NOT skip mandatory ones.
